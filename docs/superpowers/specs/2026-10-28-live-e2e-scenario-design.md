# Live E2E-сценарий по всему CWM Public API — дизайн

Дата: 2026-10-28. Основа: `main` (1.1.0, снимок `docs/openapi/swagger-v4.25.0b.json`, 170 операций в
`tests/api/api_coverage_manifest.py`).

## Зачем

Офлайн-тесты доказывают, что каждая операция спецификации имеет метод-обёртку и что метод шлёт правильный
verb/path/body. Они не доказывают, что живой сервер принимает эти запросы и что ответы проходят наши
модели (`extra="forbid"`). Нужен один прогон против реального стенда, который последовательно вызывает
все операции API в «штатном» режиме, создаёт все виды объектов в своих временных пространствах, в конце
всё удаляет и печатает отчёт: какая операция прошла, какая упала, какая пропущена и почему.

## Цели

- Один сценарий от создания пространств до их удаления, который вызывает каждую из 170 операций, кроме
  явно исключённых политикой безопасности (ниже).
- Задействовать все виды объектов: пространства, папки, статусы, workflow, типы, атрибуты всех 7 типов
  (`UniString`, `Number`, `Date`, `UniSelect`, `Tag`, `User`, `TimeDuration`) с опциями, роли, рабочие
  элементы (родитель/потомок), значения атрибутов, комментарии и их видимость, связи (в том числе между
  двумя пространствами), шаринг, вложения с версиями, документы с версиями/статусами/блокировкой,
  agile и спринты, портфели и их элементы, метрики времени, git-токены, участники и группы с ролями.
- Отчёт, где по каждой операции видно: PASS / FAIL / SKIP / EXCLUDED, шаг, длительность, текст ошибки.
- Покрытие считается **по факту вызовов** (перехват на уровне транспорта), а не по декларации.

## Не цели

- Негативные проверки (ошибочные коды, валидация, 409 и т. п.) — следующий этап.
- Нагрузка, параллельность, измерение производительности.
- Запуск в CI на каждый коммит.

## Анти-цели (провал, даже если всё «зелёное»)

- Изменение любых данных, которые прогон не создал сам: чужие пространства, учётные записи
  пользователей, группы, сохранённые запросы.
- Вход в админские настройки инстанса (OpenID-подключения, блокировка пользователей).
- Удаление чего-либо по совпадению имени, а не по id из реестра прогона. Единственное исключение —
  уборка забытых пространств (ниже), и там совпадения имени мало: нужны все признаки сразу.
- Утечка токена в лог, отчёт или файл.

## Ограничения

- Стенд и токен — из `.env` (`BASE_URL`, `API_TOKEN`), как у примеров. Других обязательных переменных нет.
- Тест запускается только явно: `RUN_LIVE_E2E=1`. Без флага `pytest` его пропускает, CI на стенд не ходит.
- Демо-пользователи: логины `demo.user1`, `demo.user2`, … Нужны четыре: `demo.user1..4`. Их учётные
  записи не меняются, они только добавляются в наши пространства и убираются из них.
- Известные причуды живого стенда (CLAUDE.md, `AGENTS.md`): привязка атрибута к типу может вернуть 500;
  создание задачи с непривязанным атрибутом — 404; связь с элементом портфеля может закоммититься и упасть
  на валидации ответа; `workitems.list(name=...)` давал 500; создание задачи без описания — 400.
  Сценарий всегда передаёт `description`, не использует фильтр `name` у `workitems.list`, после
  `link_workitem` перечитывает состояние, а не повторяет запрос. Неидемпотентные записи не повторяются.

## Политика безопасности → исключённые операции (7)

| Операция | Почему исключена |
|---|---|
| `BlockUser`, `UnblockUser` | меняет учётную запись существующего пользователя |
| `GetConnections`, `CreateConnection`, `DeleteConnection`, `CreateUser` (OpenID) | админские настройки инстанса |
| `UpdateQueryVisibilitySettings` | меняет чужой сохранённый запрос |

Они попадают в отчёт со статусом `EXCLUDED`. Итог отчёта: «вызвано X из 163, исключено 7».

## Операции, зависящие от данных стенда

- `ListQueryWorkitems`, `GetQueryVisibilitySettings` — создать запрос через API нельзя. Берём
  `E2E_QUERY_ID` и `E2E_QUERY_WORKSPACE` из окружения (только чтение). Не заданы → `SKIP`.
- `ListUserGroups`/`GetUserGroup` и операции `WorkspaceGroups` — нужна существующая группа. Берём
  `E2E_GROUP` (имя), иначе первую из `groups.list()`. Группа только добавляется в наше пространство и
  убирается. Групп нет → `SKIP` для зависящих операций.
- 9 операций метрик времени — нужен шаблон метрики в новом пространстве; создать шаблон через API нельзя.
  Нет шаблонов в `workitem_metric_templates.list()` → `SKIP` с причиной. (Есть ли шаблон по умолчанию в
  новом пространстве — неизвестно, выяснится первым прогоном.)
- `TimeTracking` — только чтение за период прогона с фильтром по демо-пользователям; пустой ответ — PASS.

## Сценарий

Префикс прогона: `E2E` + 6 символов base36 от UTC-секунды старта; пространства `<префикс>A` и `<префикс>B`
(ключ пространства — не больше 10 заглавных букв/цифр, проверено на стенде; полное время — в имени). Каждый созданный объект сразу пишется в реестр.

**0. Предполётная проверка (только чтение).** `workspaces.list(key=…)` (заодно проверка авторизации:
401/403 → прогон `BLOCKED` до любой записи), `users.list`, `users.get` для `demo.user1..4` (не нашлись →
`BLOCKED`), `groups.list/get`, `providers.list`, `statuses.list_categories`, `work_calendars.list`.

**1. Пространства.** `workspaces.create` A и B → `get` → `patch` (описание) → `list(key=…)`.

**2. Участники и роли.** `roles.list` → `roles.create` (набор `Permission`) → `get` → `patch`.
`workspace_users.add` demo.user1..4 в A, demo.user1 в B → `list` → `add_role` (наша роль) → `get_roles` →
`remove_role`. `workspace_groups.add` → `list` → `add_role` → `get_roles` → `remove_role` → `remove`.

**3. Структура.** `folders.create` корневая (parent = id пространства) и вложенная → `get` → `list` →
`patch`. В B — одна корневая папка.

**4. Процесс.** `statuses.list` → `statuses.create` ×2 (категории из `list_categories`) → `statuses.get`.
`workflows.create` (статусы + переходы) → `get` → `list` → `patch` (имя).

**5. Атрибуты.** `attributes.create` по одному на каждый из 7 типов (`UniSelect` и `Tag` — с опциями) →
`get` → `list` → `patch` → `add_option` → `patch_option` → `delete_option` (на `UniSelect`).

**6. Типы.** `types.list` → `types.create` (наш workflow, без атрибутов) → `add_attribute` ×7 → `get` →
`patch` → `remove_attribute` (один атрибут, затем снова `add_attribute`, чтобы задача могла его заполнить).

**7. Agile.** `agile.create` (на корневой папке) → `get` → `list(folder_id)`. `sprints.create` (команда
demo.user1..2) → `get` → `list` → `patch`.

**8. Портфели.** `portfolios.create` → `get` → `list` → `patch`. `portfolio_elements.create`
(ответственный demo.user1) → `get` → `list` → `patch`.

**9. Рабочие элементы.** В A: родитель нашего типа со значениями всех 7 атрибутов, исполнитель
demo.user1, в спринте; потомок под родителем. В B: одна задача (тип и workflow — первые существующие в B).
`workitems.get` → `list` (фильтры `type`, `sprint_id`, `parent`, `assignee`, `status`) → `count` →
`list_updates` (с начала прогона) → `list_by_parent` → `patch` (статус по переходу, оценка).
`workitems.list_attributes` → `update_attribute` по каждому из 7 типов.
`portfolio_elements.link_workitem` → перечитать → `workitems.list(portfolio_element_id)`.

**10. Взаимодействие с задачей.** Комментарии: `create` → `list` → `update` → `get_visibility` →
`update_visibility` (`OnlySelected`, demo.user2). Связи: `links.list_types` → `create` A→B (с
`linked_workspace`) → `list`. Шаринг: `create` (demo.user3, `Read`) → `list` → `patch` (`Comment`).
Вложения: `upload` (маленький детерминированный файл) → `upload` той же `attachment_id` (версия 2) →
`list` → `list_versions` → `get` → `get_version` → `download` (сравнить байты).
Метрики времени (если есть шаблон): `templates.list` → `enable` → `list` → `get` → `update` → `start` →
`pause` → `resume` → `stop` → `disable`.

**11. Документы.** `document_statuses.list` → `get`. `documents.create` → `get` → `list` → `patch`
(статус) → `block` → `unblock`. Версии: `document_versions.list` → `get`. Комментарии: `create` → `list`.
Связь с задачей: `document_workitem_links.create` (задача из B, `workitem_workspace`) → `list` →
`list_by_workitem`. Шаринг: `create` (demo.user4) → `list` → `patch`. Вложения — как у задачи.

**12. Интеграции.** `git_integration_tokens.create` (`GitLab`) → `get` → `list` → `update` → `refresh`.

**13. Глобальное чтение.** `time_tracking.list`, `list_updates`; `queries.list_workitems`,
`get_visibility` (если задан запрос).

**14. Удаление в обратном порядке.** Токен; вложения документа (`delete_version`, `delete`,
`delete_all`); шаринг, связь, комментарий документа; версия документа (`delete_version`, только если версий
≥ 2, иначе `SKIP`); документ. Вложения задачи (`delete_version`, `delete`, `delete_all`); шаринг; связь;
комментарий; `unlink_workitem`; задачи (потомок, родитель, задача B). Элемент портфеля, портфель; спринт;
agile; тип; атрибуты; workflow; роль (`delete` с `replacement_role_id` системной роли); участники
(`workspace_users.remove`); папки (вложенная, корневая). Статусы не удаляются (нет операции) — уходят
вместе с пространством. В конце `workspaces.delete` B и A.

**Страховка.** Уборка в `finally`: если сценарий прервался, удаляются только пространства из реестра
прогона (удаление пространства уносит всё внутри). Если и это не удалось — отчёт печатает ключи
оставшихся пространств; их уберёт следующий прогон (ниже).

## Идемпотентность: уборка забытых пространств

Цель: прогон, упавший или прерванный (Ctrl+C, обрыв сети, убитый процесс), не оставляет мусор
навсегда, и каждый следующий прогон стартует с одинакового состояния стенда. Всё, что создаёт сценарий,
живёт внутри его двух пространств (глобальных сущностей он не создаёт), поэтому достаточно удалять
забытые пространства целиком.

Маркировка при создании: ключ `E2E<base36 время>A|B`, а в описании пространства — строка-маркер
`teamstorm-api-examples live e2e run <префикс>`. Маркер сохраняется и после `patch` описания в шаге 1.

Уборка — отдельный шаг сразу после создания пространства A (тогда известен автор, то есть пользователь
токена: публичного API «кто я» нет, а `WorkspaceModel.author` заполняется сервером). Пространство
удаляется, только если выполнены **все** условия:

1. ключ соответствует шаблону `^E2E[0-9A-Z]{6}[AB]$`;
2. описание содержит маркер, а префикс в маркере совпадает с префиксом ключа;
3. автор — тот же пользователь, что у только что созданного A;
4. метка времени в ключе старше 6 часов (защита от одновременного прогона с другой машины);
5. это не пространство текущего прогона.

Каждое такое удаление попадает в отчёт отдельным разделом «уборка прошлых прогонов» (ключ, возраст,
результат) и не влияет на статусы операций. Ошибка удаления забытого пространства — предупреждение,
не FAIL. Тот же шаг можно запустить отдельно, без сценария:
`RUN_LIVE_E2E=1 E2E_CLEANUP_ONLY=1 .venv/bin/python -m pytest tests/e2e -s` — тогда пространство A не
создаётся, а автор определяется из `E2E_OWNER` (логин владельца токена); без `E2E_OWNER` режим только
печатает кандидатов и ничего не удаляет.

## Поведение при сбое шага

Шаг — именованная функция с явным списком того, что ей нужно из реестра (`needs`) и что она создаёт.
Упал шаг → его операции FAIL, все шаги, которым нужен его результат, — SKIP с причиной «нет X», прогон
идёт дальше. Шаги удаления выполняются всегда, если их объект есть в реестре. Итог pytest: тест падает,
если есть хотя бы один FAIL; SKIP и EXCLUDED не роняют тест, но видны в отчёте.

## Отчёт

По контракту из `.agents/skills/teamstorm-api/references/smoke-testing.md`: коммит Git, хост без
учётных данных, UTC начала/конца, ключи и id пространств, созданные id, мутации были/не были,
оставшиеся объекты. Таблица по 170 операциям: `operation_id`, метод/путь, статус, шаг, длительность,
ошибка (HTTP-статус + обрезанное тело, без заголовков). Итоги по статусам. Вывод в консоль (сводка +
FAIL/SKIP) и файлы `build/e2e/<префикс>.md` и `.json` (`build/` уже в `.gitignore`).

Статус операции определяется перехватом реальных HTTP-вызовов: обёртка-подкласс `TsClient` записывает
каждый `(метод, путь, статус ответа, длительность)`, путь сопоставляется с шаблонами манифеста.
Операция PASS, если хоть один её вызов прошёл и шаг не упал на разборе ответа.

## Офлайн-проверка (в обычном `pytest`)

Тест без сети: множество операций, которые шаги объявляют, ∪ исключённые = все 170 операций манифеста,
без лишних и без пересечения исключённых с объявленными. Так новый эндпоинт, добавленный в манифест,
сразу роняет тест, пока его не включат в сценарий или в исключения.

## Решения, принятые мной (проверьте)

- Расположение: `tests/e2e/` — пакет со сценарием, раннером/отчётом, opt-in тестом
  `test_live_e2e.py` и офлайн-тестом полноты. Запуск:
  `RUN_LIVE_E2E=1 .venv/bin/python -m pytest tests/e2e -s`.
- Два пространства: второе нужно для межпространственной связи и для связи документа с задачей из
  другого пространства.
- Кто читает отчёт — не уточняли; исходил из ручного запуска перед релизом обёртки под новую версию API.
- Группа для `WorkspaceGroups` по умолчанию — первая из списка, если не задана `E2E_GROUP`.
- Уборка забытых пространств — по серверным признакам (ключ + маркер + автор + возраст > 6 ч), а не по
  локальному файлу, чтобы работала и после прогона с другой машины.
- Сопоставление факта вызова — через перехват `TsClient._request` (единственная точка всех HTTP-вызовов).

## Оставлено исполнителю

Конкретные имена, значения атрибутов, набор `Permission` у роли, координаты статусов в workflow, формат
markdown-таблицы, внутреннее устройство реестра и шагов — по вкусу, в стиле существующих тестов.

## Факты стенда, выяснившиеся при первых прогонах (2026-10-28)

- Ключ пространства: не длиннее 10 символов, начинается с заглавной буквы, только заглавные буквы и цифры.
- `GET /users/{username}` для `demo.user1` вернул `demo.user12` (совпадение не точное): пользователи ищутся
  через `users.list(username=…)` с точным сравнением, `users.get` вызывается по id.
- Документ с родителем-папкой — 404 «Node not found»; документ создаётся в корне (parent = id пространства).
- Спринт в agile со story points требует `estimated_story_points`.
- Тип связи принимается по id, не по key.
- Новую версию вложения через API не создать (повторная загрузка — `File.Conflict`), поэтому у каждого вида
  удаления вложения своё вложение; у документа одна версия — `DeleteDocumentVersion` = SKIP.
- В новом пространстве статусы документов выключены — `PatchDocument` = SKIP; шаблонов метрик времени нет —
  9 операций метрик = SKIP.
- Ошибки обёртки, найденные прогоном (исправлены отдельным коммитом): `list_versions` и `get_version` у вложений
  задач и документов (сервер отвечает конвертом `{"items": [...]}`), `portfolio_elements.link_workitem`
  (ответ `{"elements": [...]}` вместо `PortfolioElementModel`).
